# Kritva SDK Testing Strategy

**Status:** APPROVED strategy with the gates below implemented for KOS-SDK-001 to 003 (program acceptance pending). Gates not listed in the table are not implemented.

| Level | Purpose |
|---|---|
| Unit | Config, models, errors and compatibility checks (client lifecycle when a client exists) |
| Contract | Upstream schemas, versions and error mapping |
| Integration | Actual service boundaries and transport behavior |
| Regression | Preserve accepted API and behavior guarantees |
| Example smoke | Run examples against mocks or simulation |
| Security | Dependency, secret and logging boundaries |

Base unit/contract suites run without hardware, ROS 2, live Control Plane or simulator. Integration reports identify mocks versus real endpoints. Simulation evidence is labelled simulation.

Kritva V2 requires `make check`, `make lint`, `make test-unit`, `make test-integration`, `make test-regression`, `make test`, `make docs-check` and `make acceptance`. Until implemented, a gate must report NOT_IMPLEMENTED and exit non-zero; it must never silently pass.

Evidence records exact commit SHA, CI run ID, command, result, environment and skipped dependencies.

## Sense contract conformance (KOS-SDK-003)

- **Fixtures (AC-005, offline).** `tests/data/sense/` holds byte-exact copies of the upstream Sense fixtures (kritva-sense `v0.2.0`, commit `543f5743d6ffd8fa1ed1ee5fdbf8295ae6a69a77`) with `PROVENANCE.json`. They are authored upstream, never generated by the SDK validator. `tests/unit/test_sense_fixtures.py` runs them on every `make test-unit`. `make schema-drift` verifies their hashes and, with `--upstream DIR`, the exact upstream commit.
- **Oracle cross-validation (AC-008).** `make conformance-test` compares `kritva_sdk.sense` with the pinned kritva-sense validator, generator and conformance harness on the fixtures, generated samples and faults, harness cases and seeded mutations, and requires identical (code, path, message) results. kritva-sense is a test-only oracle named by `KRITVA_SENSE_ORACLE` (a checkout at the recorded commit); the SDK has no runtime dependency on it and its installation never fetches it. With `KRITVA_REQUIRE_ORACLE=1` (CI) an unavailable oracle fails the run; locally the oracle tests skip with an explicit reason. A checkout at any other commit always fails.
- **Not covered.** Freshness, sequence continuity and the usability decision are context-dependent and not implemented by the SDK, so they are not tested here.

## Gates (implemented)

| Gate | Command | What it does | Needs |
|---|---|---|---|
| Structure | `make check` | Required planning files exist; commit-message checker tests pass | none |
| Lint | `make lint` | `scripts/lint.py`: syntax, unused and wildcard imports, bare except, mutable defaults, whitespace, no `print` and no forbidden import (network, ROS 2, jsonschema, kritva-sense) in the library | none |
| Unit | `make test-unit` | `tests/unit`, including the tests of the gate scripts | none |
| Integration | `make test-integration` | `scripts/integration_gate.py --full`: INT-01 offline isolated import, INT-02 wire round trip, INT-03 negative path and no secrets in errors, INT-04 provenance drift, INT-05 oracle parity, INT-06 packaging, INT-07 JSON Schema subset | `make oracle-fetch`, PyPI or `KRITVA_WHEELHOUSE`, `jsonschema` |
| Regression | `make test-regression` | `scripts/regression_gate.py`: REG-01..07 against `tests/regression/golden` ([inventory](tests/regression/REGRESSION_INVENTORY.md)) | none |
| Combined | `make test` | unit, integration and regression once each, shown separately | as integration |
| Docs | `make docs-check` | Relative Markdown links resolve (vendored upstream files excluded) | none |
| Acceptance | `make acceptance` | `scripts/acceptance_gate.py --full`: automatable criteria of KOS-SDK-001..003 from `tests/acceptance/ACCEPTANCE_MAP.json`; manual criteria are listed and never reported as passed | as integration |

A failed, skipped or missing scenario is never a pass: a skip exits 4 (INCOMPLETE). `jsonschema` and kritva-sense are test-only; the SDK has no runtime dependency on either. CI (`gates` workflow) runs all of these with the pinned oracle and `KRITVA_REQUIRE_ORACLE=1`. Software conformance is never physical or safety validation.
